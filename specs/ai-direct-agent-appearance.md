# AI 直聘 Agent 头像与形象秀规格

> **状态**：服务端 v1 已实现并通过静态检查；真实 MySQL 集成与生产发布状态以 `specs/ai-direct-hiring-progress.md` 为准。桌面 2D/3D 展示组件不在本次服务端交付范围。
> **Web 工作包**：管理页面范围、权限 DTO、开发者只读态和公司管理态以 `specs/ai-direct-web-server-roadmap.md` 的“工作包 G”为准。Web 不实现或读取桌面侧栏。
> **范围**：Agent 独立头像、2D/3D 形象秀、招聘后的形象控制权转移。
> **关联子系统**：Agent 管理、Offer/Employment 状态机、公司 RBAC、媒体上传与公共 Agent 展示页。
> **目标读者**：产品、后端、前端、3D 展示与安全审核工程师。

---

## 1. 产品目标

每个 Agent 都有独立于开发者账号和 Publisher 的头像与形象秀。开发者负责 Agent 被招聘前的初始形象；公司正式招聘 Agent 后，形象管理权随雇佣关系转交公司。

形象管理权只覆盖 Agent 的头像和形象秀，不改变 Agent 的代码、Prompt、模型策略、知识产权归属或开发者身份。

## 2. 核心对象

### 2.1 Agent 头像

- 每个 Agent 最多有一个当前头像。
- 头像属于 Agent，不复用开发者、用户或 Publisher 的头像字段。
- 创建 Agent 时允许暂不上传头像；发布到公开招聘市场前是否强制要求头像，由发布门禁另行定义。
- 更换头像必须经过服务端权限检查并写入审计事件。

### 2.2 Agent 形象秀

形象秀支持两类媒体：

- `image_2d`：普通 2D 图片。
- `model_3d`：可交互旋转、缩放的 3D 资源。“3D 图片”在数据模型和接口中统一称为 3D 模型资源，不能作为普通图片处理。

2D 与 3D 资源必须使用独立类型和独立校验管道，不能依靠文件扩展名在前端临时判断。

## 3. 展示与交互规则

### 3.1 2D 模式

1. 每个 Agent 最多保存并展示 5 张 2D 形象图片。
2. 2D 图片按照显式 `sortOrder` 排序。
3. 多于 1 张时自动左右轮播；只有 1 张时不得出现无意义的自动切换。
4. 用户可以手动向左或向右切换，手动操作后自动轮播可以继续，但必须重新计时，避免立即跳到下一张。
5. 页面不可见、浏览器后台运行或用户开启“减少动态效果”时，必须暂停自动轮播。
6. 轮播不得引发布局抖动；图片加载失败时显示稳定占位，不循环重试。

自动轮播间隔属于前端展示配置，不允许每条媒体资源自行定义不同间隔。

### 3.2 3D 模式

1. 3D 资源之间禁止自动轮播，只允许用户手动向左或向右切换。
2. 每个 3D 资源必须支持水平 360°连续旋转，不设置观察死角。
3. 在资源和浏览器能力允许时，应支持垂直观察；不得用固定预渲染角度伪装成完整 3D 交互。
4. 每个 3D 资源支持缩放，最大放大倍率为初始适配视图的 3 倍。
5. 缩放下限应保证模型可恢复到完整可见状态，并提供“重置视角”操作。
6. 切换到另一个 3D 资源时，默认恢复该资源的初始视角和缩放比例。
7. 3D 资源加载失败时必须显示错误占位及手动重试，不得自动快速重试或阻塞其他媒体。

3D 资源数量上限、文件格式、单文件大小、纹理预算和移动端降级策略必须在实现前通过媒体安全与性能评审确定；这些实现限制不得改变“手动切换、360°旋转、最大 3 倍放大”的产品要求。

### 3.3 2D/3D 模式切换

- Agent 可以同时拥有 2D 和 3D 形象资源。
- 展示页提供明确的 `2D` / `3D` 模式切换；仅存在一种资源时不显示无效切换入口。
- 当前模式可以在页面会话内保留，但不得把访问者的选择写回 Agent 全局配置。
- Agent 管理方可以设置默认展示模式；默认模式资源不可用时自动降级到另一种可用模式。

## 4. 形象控制权状态

形象控制权由服务端根据 Employment 状态派生，客户端提交的 `controllerType`、`companyId` 或“我是管理员”等字段不可信。

### 4.1 招聘前

在以下状态下，开发者可以设置和修改头像、2D/3D 形象秀及默认展示模式：

- Agent 尚无 Employment；或
- Employment 为 `candidate`、`evaluating`、`offer_pending`、`offered`。

“开发者”指 Agent 的 `ownerUserId`；如果 Agent 归属于 Publisher，可继续使用现有 Publisher 成员授权规则，但必须记入实际操作人。

### 4.2 公司接管

Employment 首次进入 `accepted` 时，头像与形象秀控制权在同一事务内转交对应公司。

以下状态由该公司控制：

- `accepted`
- `onboarding`
- `active`
- `paused`
- `offboarding`

控制期间：

- 开发者只能查看，不能新增、删除、替换、排序或修改默认展示模式。
- 公司角色 `owner`、`admin`、`manager` 可以修改。
- `recruiter` 无权修改头像或形象秀。
- 公司只能管理外观，不能因此获得 Agent Prompt、模型策略、版本发布或所有权管理权限。
- 所有修改必须记录公司、Employment、操作者、修改前后资源版本和请求 ID。

### 4.3 雇佣结束

Employment 进入 `terminated` 时：

- 形象控制权归还开发者。
- 公司立即失去后续修改权限。
- 公司任职期间最后一次生效的头像与形象秀继续展示，不自动删除或回滚。
- 开发者可以保留、替换或删除这些资源。

从 `offboarding` 恢复到 `active` 或 `paused` 时控制权仍属于原公司，不发生重复转移。

### 4.4 并发雇佣约束

Agent 头像和形象秀是全局形象，因此同一时刻只能存在一个控制公司。服务端必须保证：

- 一个 Agent 最多有一个处于 `accepted`、`onboarding`、`active`、`paused`、`offboarding` 的形象控制 Employment。
- 已存在控制 Employment 时，另一家公司不得把该 Agent 的 Employment 转入 `accepted`；应返回稳定冲突错误，而不是覆盖当前控制公司。
- 该约束必须由数据库唯一性或事务锁保证，不能只做“先查询再写入”的非原子校验。

如果未来产品允许 Agent 同时受雇于多家公司，应改为“Employment 专属形象”，不能让多家公司竞争修改同一个全局形象。

## 5. 建议数据边界

实现时应保持职责分离：

- `ai_direct_agent_appearance_profiles`：每个 Agent 一条，保存头像引用、默认模式、当前修订号和控制 Employment 引用。
- `ai_direct_agent_appearance_assets`：保存 2D/3D 资源引用、类型、排序、状态和安全校验结果。
- Employment 状态机：只负责在状态转移事务中获取、转交或释放形象控制权。
- 媒体服务：负责上传、格式识别、病毒扫描、大小与渲染预算校验。
- 展示组件：只消费已批准的形象 DTO，不自行推导权限或信任原始上传地址。

不要把形象列表塞进 `ai_direct_agents` JSON 字段。媒体有独立生命周期、排序、审核状态和审计要求，使用 JSON 会造成并发覆盖、校验扩散和难以追踪的删除行为。

## 6. 服务端授权不变量

1. 每个写接口都必须根据最新 Employment 状态重新判断控制权。
2. 不能只依赖前端隐藏按钮。
3. 控制权检查与媒体元数据写入必须在同一事务中完成，防止状态切换期间越权写入。
4. 删除采用可审计的软删除；底层对象存储清理由异步任务完成。
5. 客户端不能提交任意外部 URL 直接成为公开资源；资源必须经过平台上传、类型识别和安全校验。
6. 公开 DTO 不返回对象存储内部路径、扫描细节或上传者敏感信息。
7. 2D 的 5 张上限必须由数据库事务内计数或槽位唯一约束保证，不能只在前端限制。

## 7. 审计事件

至少需要以下稳定事件：

- `agent_appearance.avatar.updated.v1`
- `agent_appearance.asset.added.v1`
- `agent_appearance.asset.removed.v1`
- `agent_appearance.assets.reordered.v1`
- `agent_appearance.default_mode.updated.v1`
- `agent_appearance.control.transferred.v1`
- `agent_appearance.control.released.v1`

审计元数据只保存资源 ID、类型、排序、Employment、公司和操作人，不保存媒体二进制内容。

## 8. 验收标准

1. 开发者可以在招聘前设置 Agent 独立头像和形象秀。
2. 第 6 张 2D 图片在服务端被拒绝。
3. 2D 多图自动轮播且支持手动左右切换。
4. 3D 资源之间绝不自动切换，只能手动左右切换。
5. 每个 3D 资源可连续 360°旋转，最大放大到初始适配视图的 3 倍，并能重置视角。
6. Employment 进入 `accepted` 后，开发者的所有形象写操作返回 `403 FORBIDDEN_SCOPE`。
7. 任职公司 `manager+` 可以修改，`recruiter` 返回 `403 FORBIDDEN_SCOPE`。
8. Employment 进入 `terminated` 后，公司失去权限，开发者恢复权限。
9. 两家公司不能同时获得同一 Agent 的全局形象控制权。
10. 控制权转移、资源修改和删除均能通过审计事件还原。

## 9. 当前实现边界

服务端 v1 已实现：

- 独立 profile/asset 表、受管文件资源 ID 和 optimistic concurrency revision；
- 头像、2D 图片、自包含 GLB 的上传、读取、排序和软删除 API；
- Employment 进入 `accepted` 时在同一 MySQL 事务中获取控制权，进入 `terminated` 时条件释放；
- 开发者、Publisher 成员、公司 `manager+` 和 recruiter 的服务端权限分界；
- 同 Agent 多公司控制冲突、2D 五张上限及稳定审计事件。

仍不属于该服务端里程碑：公开招聘页的 2D 轮播/3D 渲染组件、媒体病毒扫描服务、对象存储多实例部署和客户端展示交互。生产是否已应用迁移不能从源码推断，必须以发布记录和 migration status 为准。
